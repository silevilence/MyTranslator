# ADR-0002：标记提取模型 — 内联标记占位符化

- 状态：已接受（2026-08-13）
- 范围：后端文件导入拆解/导出模块、AI 翻译输入格式、规则引擎、`docs/back` 分段接口契约
- 相关：[CONTEXT.md](../../CONTEXT.md)、[ROADMAP.md](../../ROADMAP.md)「后端：文件导入拆解与导出」

## 背景

文件导入需支持 txt / markdown / html（含 epub、URL）。markdown 标记与 html 标签是**不可翻译的结构信息**：翻译期间必须原样保留、导出时还原，否则译文无法回填成合法文件。ROADMAP 已要求「特殊标记/占位符提取与回填」。两种实现路线：

- **提取模型**：解析器把内联标记从可译文本中剥离，替换为占位符引用，标记原文存入分段的标记表。
- **内联保留模型**：标记留在段内文本中，靠 AI 遵守提示词 + 规则引擎事后比对是否被改动。

## 决策

1. **内联标记一律按提取模型处理**：段内可译文本以**成对占位符引用**表示标记——`<xN>`（开）、`</xN>`（闭）、`<xN/>`（自闭合），OmegaT 风格；标记原文（如 `<b>`、`**`、`[text](url)` 的完整原文、html 实体）按编号存储于该分段的标记表。成对关系在段文本中直接可见。
2. **实体与标签一样占位符化**：`&amp;`、`&nbsp;` 等实体不解码进可译文本，作为占位符带入译文；标记表记录**原文与人类可读含义**（如 `&nbsp;` → 不间断空格），译者可查看。
3. **块级结构**（html 块级标签、markdown 标题/列表/引用/表格等）由格式解析器决定分段边界与段首尾占位符；块级标签作为段首尾占位符回填，**不丢失**。具体规则在 `docs/back` 接口约定与各格式设计文档中定义。
4. **无可译文本的内容**（代码块、分隔线、markdown 内嵌 HTML 块等）不产生分段，作为受保护块原样存储，导出原位还原。
5. **导出 = 按引用回填**：段序与受保护块交错还原原文，保证「导出格式与原文件一致」由构造保证。

## 理由

- 与已规划的 AI 翻译「占位符保护」和规则引擎「占位符保留检查」共用同一数据结构，三处契约天然对齐。
- 「格式一致」由构造保证，不依赖 AI 行为正确性。
- OmegaT 等成熟 CAT 工具的 HTML/标记过滤器即此做法，有成熟经验可借鉴。

## 后果

- 正向：占位符保护与规则检查全格式统一；导出保真是确定性结果。
- 反向：段内文本带 `{N}` 引用，人/AI 阅读略碎；每个格式需要可靠的解析器（html 用成熟 HTML 解析器、markdown 用 AST 解析器）才能正确提取标记。
- 分段 API 契约需包含：分段文本（含 `<xN>` 引用）、标记表（编号 → 原文 + 含义提示）、受保护块。
- 段文本中可能出现的字面 `<xN>` 文本与引用冲突：编号规则需规避（实现细节，另行约定）。

## 替代方案

- **内联保留模型**：标记留在段内，规则引擎模糊比对标记是否被改动——校验脆弱，「格式一致」成为概率事件而非构造保证（拒绝）。
- **块级结构存入分段元数据而非占位符**：数据结构更复杂，且规则引擎/AI 输入需感知两种载体（未采纳，保持单一 `<xN>` 引用机制）。
- **实体解码入文本**：`&nbsp;` 等以真实字符进入译文、导出统一转义——翻译可读性更好，但「逐字节还原」变成「语义还原」（拒绝，本方案下 html 导出保持逐字节）。
